Your app works on your desk. Does it survive a real phone?

droid-monkey attacks any Android app with what real phones do to it, hunts for bugs in normal use, and fixes what breaks, with your consent. Every fix is proven by replaying the identical attack on a running device, plus a new regression test.

Three ways it finds problems

Faults that phones cause. Bugs that are just there. Screens that lose users.

Most bugs that reach users don't show up when you tap through the app on a fast emulator with a stable connection, and some problems never crash at all. droid-monkey looks for all three.

(x_x) attack

Real-world faults, injected on purpose

Android kills your app in the background, the user rotates mid-load, the network drops, a permission gets revoked in Settings, memory runs low, the CPU is busy. droid-monkey does exactly that to every screen that matters, and measures what breaks.

droid-monkey attack builtin --diagnose
(o_O) hunt

Bugs in normal use, no fault needed

It walks every journey like a customer and checks after each step:

  • the app's own logs: crashes, exceptions it caught and hid, main-thread jank
  • every screen: null, NaN, an unfilled %d, negative money
  • the whole journey, read by a model: numbers that don't add up across screens

(o.o) ux

A UX audit of every screen

Where the eye goes, how long each tap makes the user wait, and what a finger or a screen reader can't use:

  • a predicted attention heatmap for every screen
  • waits measured on the device against Nielsen's limits
  • tap targets under 48 dp and unlabelled controls
  • a model's review of each screenshot, written as a change to make

UX audit, on Wikipedia for Android

An app can work and still lose its users.

Nothing crashes when a new user can't find the way forward, waits two seconds after a tap, or meets a switch that TalkBack reads as "View". droid-monkey ux looks for these on every mapped screen. On the open-source Wikipedia app it mapped 40 screens with no changes to the app, and the audit cost $1.17.

How the audit helps

See what users will miss

A saliency model, combined with the screen's UI structure, predicts where the eye goes and the share of attention each control gets. When the main action loses to a link or an image, you see it before users skip it.

Measured, not guessed

Every wait is timed on the device against Nielsen's limits (0.1 s instant, 1 s keeps the flow, 10 s loses attention). Touch targets are measured in dp, labels read from the UI dump, taps counted from launch.

A change, not just a complaint

A model reviews every screenshot with the code behind it and writes each finding as a concrete change: what to edit, in which file, and why it matters to the user.

Your yes, then proof

droid-monkey ux asks about each finding. Say yes and a coding agent makes the change. It's discarded if the app doesn't build; otherwise droid-monkey reopens the screen for a before/after screenshot and commits it. Findings also join the ranked issues list.

What the agent suggests changing in Wikipedia

The 7 findings seen on the device, each with the change the review proposed. They are proposals: droid-monkey made no changes to Wikipedia. Run droid-monkey ux on your own app and it asks about each one.

highnavigation

Stop the Year in Review promo from covering a just-opened article

Seen: tap the featured article, wait 1.2 s, and get a full-screen Year in Review takeover instead of the article, with "not enough activity" for a personal review.

Change: show announcements only on the main screen, not on PageActivity; if they must stay on articles, wait until the article has loaded and the user has scrolled.

BaseActivity.kt · YearInReviewOnboardingActivity.kt
mediumattention

Give onboarding a visible, labelled Continue button

Seen: "Learn more" draws 16× the attention of the Forward arrow; on interests, Next ranks 7th of 8. Home is 5 taps away and Skip only appears on the third screen.

Change: replace the arrow with a filled "Continue" button, show Skip on every step, and make "Learn more" smaller.

InitialOnboardingScreen.kt · PersonalizationScreen.kt
mediumaccessibility

Make settings switches labelled and tappable across the whole row

Seen: TalkBack announces six unnamed "View" controls on Community modules, three on Settings, three on the donation reminder. Only the small switch takes the tap.

Change: make the whole row one toggleable control with the switch role, so it's read as "Featured article, switch, on".

Settings.kt · CommunityModulesScreen.kt · DonationReminderScreen.kt
mediumfeedback

Show progress and a clear button on the reading-list source step

Seen: the only way forward is an unlabelled arrow, ranked last of 4 controls, and tapping it took 3.7 s with nothing on screen.

Change: a full-width "Next" button that shows progress once tapped, and start the fetch when the screen opens instead of on tap.

RecommendedReadingListSourceScreen.kt · …SourceViewModel.kt
mediumaccessibility

Enlarge and label tiny tap targets in edit history and Places

Seen: an unlabelled 16 dp-tall contribution row, a 32 dp date picker, 44 dp Map/List toggles and an unlabelled My location button, all under the 48 dp minimum.

Change: give the rows a content description and full-card height, and the toggles and date picker a 48 dp touch area.

Hide the raw mention wikitext in the talk reply box

Seen: the reply box opens with @[[User:SL93|SL93]], the most-looked-at thing on screen, 4.4× the attention of Next.

How it works

A model decides. Code judges. You approve.

One loop, built on LangGraph: checkpointed after every step, resumable after a crash, and traced end to end. Verdicts are measured on the device, never guessed by a model.

analyze→ explore→ plan→ attack→ diagnose→ ask you→ fix→ verify→ commit
decided by code, on the device waits for your yes agents and models

analyze + explore

A coding agent reads the repo, lists every screen in the code, then drives the app on an emulator to map them: each screen gets a replayable path from launch and the source files behind it.

attack + verdict

Attacks are built only from fixed, verified building blocks, never arbitrary commands. Code reads the verdict from the crash buffer, field diffs, frame stats, live Activities after a forced GC, launch times and a Perfetto trace.

diagnose

An agent reads the code with Entire's code graph and SQL over the Perfetto trace, and returns the root cause with file:line evidence, a fix approach and a test plan.

ask you

No code changes without consent. Every attempt shows the issue, the measured evidence, the root cause and the suggested change, and waits for yes, no or all.

fix

Claude Code, Codex or droid-monkey's own API agent edits only the app's sources. No shell, no docs, no git history, no build files. One extra tool: compile.

verify + commit

Rebuild, replay the identical attack, run the new test. Committed only if both pass, one commit per fix with an Entire checkpoint, on its own branch.

Every major command

init

Detects the module, package, emulator and JDK, and writes monkey.yaml.

analyze

A coding agent reads the repo: risk patterns with file:line, and the user flows worth testing.

explore

An agent drives the app from a checklist of every screen in the code, and maps each with a replayable path.

attack

Runs the 7 built-in attacks and your saved ones; code reads every verdict on the device.

attacks new · suggest · from-flows

The attack designer agent writes attacks for your app: from plain words, from your code, or from each risky user flow.

hunt

Walks every journey like a user and catches bugs in normal use: logs, placeholders, numbers that don't add up.

ux

The UX audit: attention heatmaps, measured waits, tap targets, labels, and a change for each finding.

issues · fix

Every issue from attacks, hunt and UX in one list ranked by user impact; fix one with your yes.

run

The full loop: attack, diagnose, ask you, fix, replay the identical attack, commit.

dashboard

A live local page over every run, screen, heatmap and issue; stream the emulator and run any command.

report · compare · pr

Score card and receipt, before/after tables, and a PR with the evidence.

Terminal or browser

Run it from your terminal, or all of it from your browser.

The CLI talks in monkeys: a face for every verdict, and a "Fix it?" before every change. droid-monkey dashboard serves the same thing as a live local page. Run any command from a form, watch the output stream next to the emulator's screen, answer "Fix it?" with a button, fix issues from one ranked list, and open the PR. It listens on 127.0.0.1 only.

Features

Everything droid-monkey does, end to end.

One CLI, from reading your code to a verified commit, with a live dashboard over all of it.

(o.o)

Understand the app

  • Any Android app. init detects the module, package, variant, emulator and JDK.
  • Code analysis: manifest, permissions and 10 risk patterns with file:line, plus the user flows worth testing.
  • Screen map: an agent drives the app from a checklist of every screen in the code; each gets a replayable path and its source files.
  • Four explore modes: agent, fast (no model), manual (you drive) and rules.
  • Signed-in apps through a test account.
(x_x)

Find what breaks

  • 7 built-in attacks: process death, rotation, network loss, permission revoke, low memory, CPU load, slow startup.
  • App-specific attacks from your user flows, designed by an agent, or described in plain words.
  • Hunt: bugs in normal use, from the app's logs, every screen, and a model reading each journey.
  • UX audit: touch targets, labels, attention heatmaps, measured waits.
  • One ranked list of every issue, by user impact.
  • Deep evidence: Perfetto traces, ANR stacks, leak chains from Shark, screen recordings.
(^o^)

Fix it, and prove it

  • Root-cause diagnosis with file:line evidence, Entire's code graph and SQL over the trace.
  • Your yes first: every fix shows the evidence and waits.
  • Three coding agents: Claude Code, Codex or the API agent. Sources only, no shell.
  • Proof on the device: the identical attack replayed plus a new test, or it isn't committed.
  • Recovery: revised diagnosis and retry, clean rollback, emulator watchdog, resume after a crash.
  • One commit per fix with an Entire checkpoint, and a PR with the evidence.
(^.^)

See and share the results

  • Live dashboard: every run, screen and issue; stream the emulator and run any command from the page.
  • Reports: recordings, charts, a score card and a receipt with time, tokens and cost per step.
  • Tracing: every run is one neatlogs trace.
  • Cost control: measured costs feed the cfo.ai plan, and run --tier enforces its fix budget.
  • A CLI with character: ASCII monkeys for every result, and a banana meter.

The full list, with every command and option, is in the README.

Attacks written by a model, for your app

The built-ins are generic. The bugs that matter are often specific: rotating while the order is placed, going offline right after switching a feed. The designer agent writes these as attack specs. It reads the app's analysis, user flows, screen map and source, and composes the same verified building blocks the built-ins use: 17 faults (rotate, network_off, kill_in_background, dark_mode, locale, cpu_stress…) and steps like tap, fill, wait and settle.

you describe it, or the model picks a risk→ model writes YAML→ validated in code→ tried on the emulator→ saved

To be clear about what this shows: on a small app with textbook bugs, plain Claude Code fixes everything by reading code, and faster. droid-monkey's value is what reading can't do: finding which faults actually break the app, reproducing them on a running device, proving each fix by replaying the identical attack, and the evidence trail. Its advantage grows on bigger codebases and on bugs with no stack trace. All results are single runs; details in the README.

Safe by design

It never changes your code without a yes.

Consent and isolation

Each fix waits for your answer. Fixes go on a separate droid-monkey/<run> branch, and you're put back on your own branch at the end.

Never touches a live backend

It refuses to sign up, log in, post or pay on a real backend. Signed-in screens are reached with a test account you provide.

Same source, same build

It never diagnoses a build that wasn't built from the source it's reading, and only keeps the coding agent's edits inside the app's sources.

Built with neatlogs, Entire and cfo.ai

Every run is traced, every fix is signed, every dollar is planned.

Each partner tool has a job inside droid-monkey's loop, not beside it. Full details, with the code that does each part: evidence/.

neatlogs tracing

One trace per run, with the cost of every step

droid-monkey drives other agents: Claude Code sessions analyse, explore, diagnose and fix, each in its own process. Only a trace shows the whole run and what it cost.

  • Every LangGraph node (plan, attack, decide, diagnose, approve, fix, verify, commit) and every model call.
  • Each Claude Code session as an LLM span with its exact tokens and cost. The app is the end user; the run is the session.
  • A failed or empty session is an ERROR span with the reason in claude_code.error.
  • Each check against the business plan's fix budget is a budget GUARDRAIL span.
It catches failures our own logs miss. An agent session that ends with no output looks like a success from the outside. neatlogs raised two incidents about exactly that: "Explorer returns empty response without mapping screens", which led to two fixes in droid-monkey (08fdebd, with tests), and "Diagnoser returns empty response without analyzing faults" in 13 traces, now under investigation.

cfo.ai business plan

The business plan sets what the agent may spend

droid-monkey sells as a CI add-on for Android teams. The plan is built from its own measured costs, and the plan in turn caps what each run may spend on fixes.

  1. Measure: droid-monkey econ reads every run's receipt (the same costs as the neatlogs spans) into drivers.csv.
  2. Model: cfo.ai's Ari builds three plans and six scenarios over 18 months.
  3. Enforce: the 70% margin floor sets each tier's fix budget; run --tier keeps attacking but stops fixing once it's spent.

Get started

Five commands to your first verified fix.

You need the Android SDK with one emulator, an Anthropic API key, and a coding agent (Claude Code, Codex, or just the API key). The install guide goes from an empty machine to the first run.
